# Decisions

Choices made where the SPEC was silent or unclear. One line each: `date · task · decision · reason`.

| Date | Task | Decision | Reason |
|---|---|---|---|
| 2026-11-05 | T0.1 | `config.yaml` keeps go-identity's `database.leader.max_retries`, `database.health` and `validator` blocks, which the SPEC 1.3 sample omits | `/readyz` reads the leader's health check, and the validator block lets the module `Deps` use it without another config change |
| 2026-11-05 | T0.1 | Compose Postgres logs in as `app` directly | The bootstrap script that creates the `app` role and schema arrives with migrations (T0.2) |
| 2026-11-05 | T0.1 | `server worker` holds a database connection and waits for SIGTERM | The plan's "empty runner": the outbox dispatcher and cleanup job join it in T0.6 |
| 2026-11-05 | T0.1 | Shutdown readiness is checked against the real binary, not an in-process test | The in-process test needs `testkit.Postgres` (T0.3), which carries go-identity's shutdown test over |
| 2026-11-05 | T0.2 | `testkit/postgres.go` lands with the database package instead of the rest of the test kit (T0.3) | The migration, outbox and lock integration tests need a migrated Postgres; T0.3 still adds the HTTP harness, keys and clock |
| 2026-11-05 | T0.2 | `github.com/moby/go-archive` pinned at v0.3.0 (testcontainers asks for v0.2.0) | v0.2.0 fails govulncheck (GO-2026-6253); go-identity pins the same version |
| 2026-11-05 | T0.4 | `apierr` keeps two reasons, `PERMISSION_NOT_HELD` (403) and `VERSION_CONFLICT` (409); validation (400 with `meta.fields`) and not found (404) are plain `errorz` codes | go-identity has no reason for those two; every other reason serves its sign-in flows |
| 2026-11-05 | T0.4 | `apierr.WithRetryAfter` and the Retry-After header in `httpx.Handle` are left out; `Handle` passes through to `handler.Handle` | No reason here is a 429 or a lockout; they come back with a rate limiter |
| 2026-11-05 | T0.4 | `Deps.Authz` is `authz.NewNoOp()` and `/v1/internal` has no service-token guard yet | The authorizer and the token checks arrive with auth (T1.1, T1.2); no module mounts a route yet |
| 2026-11-05 | T0.4 | The architecture test stats every file under `internal/` before running `go list` | `go list` runs in a child process the test cache cannot see, so a new cross-module import otherwise passes on a cached result |
| 2026-11-05 | T0.3 | `testkit.SigningKeys(t, iss, aud)` returns a JWKS served on a local port plus a token issuer, instead of go-identity's key directory | The template validates identity's tokens and never signs any, so its tests need what identity publishes (a JWKS) and a way to mint tokens with `sub`, `tid` and `roles` |
| 2026-11-05 | T0.3 | go-identity's `TestOperationalEndpoints` and `TestShutdownFlipsReadinessThenExits` come over with the test kit | They need `testkit.Postgres`; T0.1 checked shutdown against the real binary until now |
| 2026-11-05 | T0.6 | Stacked on T0.3 | The cleanup job takes a `clock.Clock` and its tests use `testkit.NewClock`, both from T0.3 |
| 2026-11-05 | T0.6 | The worker registers no senders, so a row on any topic stays unsent with `last_error` set until cleanup drops it after 30 days | The template sends nothing yet; a module that enqueues a topic adds its sender to `senders()` |
| 2026-11-05 | T0.5 | `scope.Owner` replaces go-identity's `scope.User`; `Session` is left out | Both read the token subject as a UUID, so keeping both would be two names for one value; refresh sessions are identity's |
| 2026-11-05 | T0.5 | `scope.Owner` reads the subject from the token claims (`auth.SubjectFromContext`), not `ctxkit.UserID` | `Tenant` already reads from the claims, and the dev claims with auth off (T1.1) only need to put claims in the context |
| 2026-11-05 | T0.5 | `OwnerFilter` returns `[]repository.FilterCondition` (empty when the caller holds the `:any` permission) | Appends straight onto `ListOptions.Filter.Conditions` with no branch at the call site |
| 2026-11-05 | T0.7 | `/swagger/*` is behind HTTP basic auth only; the token auth rule that makes it public is added with the `auth` block (T1.1) | There is no token auth yet, so no rule is needed until then |
| 2026-11-05 | T1.1 | With auth off, `LoadConfig` rewrites `authz` to `source: config`, `roles: {admin: ["*"]}`, so the loaded `Config` matches what runs | One place decides it, and `newAuthorizer` stays a plain `authz.New` |
| 2026-11-05 | T1.1 | `LoadConfig` fills empty `authz` claim names and `cache_ttl` from `authz.DefaultConfig()` before validation | `authz.Config.Validate` doesn't apply defaults (only `authz.New` does), so the YAML would otherwise have to repeat `perms_claim`, `tenant_claim`, `super_claim` |
| 2026-11-05 | T1.1 | Dev caller UUIDs are fixed: subject `00000000-0000-4000-8000-00000000d001`, tenant `…d002`, role `admin` | Rows created in one local run are still visible in the next |
| 2026-11-05 | T1.1 | `tenancy.mode` is validated (`single` or `multi`) but nothing reads it yet | The SPEC only requires it to match identity's; both modes put the tenant in `tid`, so scoped code doesn't branch |
| 2026-11-05 | T1.2 | A cached service token is replaced 30 s before its `expires_in` | Identity's service tokens live 5 minutes; 30 s covers clock skew and the role map request in flight |
| 2026-11-05 | T1.2 | `identity.client_id` and `client_secret` are both required when auth is on and `authz.source` is `identity`; neither is checked otherwise | With auth off `authz` is forced to `source: config`, so no token is ever requested |
| 2026-11-05 | T2.1 | The repository reads the tenant and owner from the context itself (`scope.Tenant`/`scope.Owner`); callers pass only `note.OwnNotes` or `note.AnyOwner` | The tenant filter can't be forgotten or supplied by a caller; "owner-scoped unless told otherwise" is one typed argument |
| 2026-11-05 | T2.1 | `note.created_by` is `NOT NULL` (the SPEC's base columns leave it nullable) | Every note is created by a signed-in caller, and the model scans it into a plain `uuid.UUID` |
| 2026-11-05 | T2.1 | `status` is checked by a `CHECK (status IN ('draft', 'archived'))` constraint | The database rejects a bad status even from a path that skips the service |
| 2026-11-05 | T2.1 | `Get` reads the leader, not a follower | `Update` calls it to tell a version conflict from a miss, and a client often reads right after its own write; lists still use `GetReadConnection` |
| 2026-11-05 | T2.1 | `NewRepository(db)` takes no logger (SPEC 1.6 shows `db, log`) | The repository returns errors and logs nothing; go-identity's repositories have the same signature |
| 2026-11-05 | T2.2 | A body naming `owner_id` or `tenant_id` is a 400 (`meta.fields`: unknown field), not silently ignored | The strict decoder rejects unknown fields; the owner and tenant always come from the token |
| 2026-11-05 | T2.2 | `Service` is a concrete struct and `note.New` returns `*Module` with no error (SPEC 1.6 shows a `Service` interface and `(*Module, error)`) | Handler tests run the real service over a mocked repository, so nothing needs a second service implementation; the config is validated at startup in `modules.note` |
| 2026-11-05 | T2.2 | Request bodies are validated in the handler; the service trusts its typed inputs | The plan puts validation in the handler step; the `CHECK` on `status` still guards the table |
| 2026-11-05 | T2.2 | `PATCH` with no field set is a 400 | It would only bump the version |
| 2026-11-05 | T2.2 | `modules.note.list_max_size` must be 1–100 | go-sdk's repository caps a page at 100, so a larger value would be silently cut |
| 2026-11-05 | T2.3 | `title=value;like` is go-sdk's case-sensitive `LIKE`; `search` is the case-insensitive option (`ILIKE` on title or body) | go-identity's `;like` (audit `action`) is a plain `LIKE` too, so the syntax means the same thing against both services |
| 2026-11-05 | T2.3 | Only `title` takes `;like`; `status`, `pinned` and `owner_id` match exactly, and a bad value (`pinned=maybe`, `owner_id=me`, an unknown status) is a 400 naming the key | Without the check, `LIKE` on a boolean or UUID column reaches Postgres as a 500 |
| 2026-11-05 | T2.3 | The default order `updated_at DESC` (then `id`) lives in the repository, not the `ListParseConfig` | `ListParseConfig` has no default-sort field; the repository already applies it when no sort is given |
| 2026-11-05 | T2.3 | `created_from`/`created_to` become `created_at >=` / `<` conditions; a date without a time is midnight UTC | go-sdk's filter builder already has `gte` and `lt`, so only `search` needed SQL in the repository |
| 2026-11-05 | T2.3 | `%` and `_` in `search` and `;like` values are not escaped | Same as go-identity; they only widen the caller's own scoped list |
| 2026-11-05 | T3.1 | Image size target read as the compressed (pushed) size: 12.7 MB; on disk it is ~36 MB, 33.8 MB of which is the stripped binary | The binary alone is over 30 MB uncompressed; shrinking it means UPX or dropping dependencies, neither worth it. GHCR and `docker pull` deal in the compressed size |
| 2026-11-05 | T3.1 | `make up` builds the image and runs the whole stack (Postgres, migrate, api, worker, Caddy, backup) without a profile; go-identity keeps those behind a `vps` profile | `SPEC 1.7` says `make up` starts the app too. The api is reached through Caddy only, so `make run` on host port 8080 still works next to it |
| 2026-11-05 | T3.1 | Postgres is published on `127.0.0.1` only and its superuser password is `POSTGRES_PASSWORD` (default `postgres`); go-identity publishes `0.0.0.0` with a fixed password | The same Compose file runs on the VPS, where a public 5432 with a known password is an open door |
| 2026-11-05 | T3.1 | Container logs reach Loki through Grafana Alloy (Docker socket), not Promtail as in guest-management-be | Promtail reached end of life; the app logs to stdout, so Alloy tails the containers instead of files |
| 2026-11-05 | T3.1 | Grafana (obs profile) allows anonymous admin and is published on `127.0.0.1:3000` | Local convenience; the Compose comment says to set an admin password before exposing it on a VPS |
| 2026-11-05 | T3.3 | The chart sets CPU and memory requests (api 100m/64Mi, worker 50m/64Mi, 256Mi memory limits); go-identity's chart leaves `resources: {}` | The HPA's CPU target is a percentage of the request; without one it never scales |
| 2026-11-05 | T3.3 | Both Deployments carry a `checksum/config` annotation of the rendered ConfigMap | Config arrives through `envFrom`, read only at start; without it a `helm upgrade` that changes config leaves the old pods running the old values (seen on kind). go-identity's chart has the same gap |
| 2026-11-05 | T3.3 | The kind install runs in a namespace enforcing Pod Security `restricted` | Closest local check of OpenShift `restricted-v2`; the real OpenShift install is T4.3 |
| 2026-11-05 | T3.4 | Release builds also carry the `sha-<short>` tag, and the image job runs only after `check` passes on a push | Same as go-identity's job; every image traces back to a commit |
